# Examples Are Not Requirements

## What this skill does

When users give examples, they usually aren't asking you to do exactly those things. They're showing you what *kind* of thing they want.

This skill's job: when you see examples, don't rush to act on them. First say in one sentence which categories they point to, then work at that level: find other members of those categories the user didn't mention, and include those too. Don't let the examples take over the answer.

## How to tell: example or requirement

Look at the user's wording.

Signals that it is an example (illustrating a type):

- 比如、比如说、例如、举个例子、打个比方、像……这种
- for example, for instance, e.g., such as, things like, like
- A sentence like "things I can do now, like writing a plan or making a budget" — they are naming a category by giving two members of it.
- A single named thing with no marker words, when the context shows it stands for a type (see Case 1 and Case 4). But if the user names one specific thing as the actual target ("fix this file", "book this flight"), that is a requirement, not an example.

Signals that it is a requirement (do exactly this):

- 就要、必须是、就做这个、照做、就要这几个、别的不用
- do exactly this, just this, only these, nothing else

Default: if the user used "for example", "such as", "比如", "例如", or an equivalent marker, treat it as an example, not a requirement.

## When the examples are real plans

Sometimes the examples are things the user actually means to do, e.g. "I want to do a few new things, like learning to bake bread or starting to run. How do I start?" Here the user wants to know about those things in their own right.

- Answer each of them concretely first: real steps they can follow.
- Then add one separate, clearly labeled section at the end for anything extra: steps they didn't mention, related things they might also like.
- Don't mix the extras into the main answer, and don't put them first.

The four steps below are for examples that illustrate a wider request ("I want to learn lots of things, like..."), not for real plans.

## Expand in four steps

When you receive examples, follow these four steps:

1. Restate the request at the category level: before anything else, say in one plain sentence which categories you can see in the examples. Name what the examples have in common, not a paraphrase of the request. E.g. for "things that help me run a podcast, like finding guests or mixing audio": "Got it: finding guests and mixing audio, one is about people and one is about sound, both things a podcast needs beyond having something to say." Don't just repeat the user's request in other words, and don't set up a contrast that corrects the user ("you want X, not just Y") when they never said Y. This sentence is how you state your assumption, so the user can correct you right away. Don't open by answering the examples themselves.
2. Identify the category behind each example: different examples can point to different categories. "Finding guests" points to outreach; "mixing audio" points to sound production. Don't force them all into one category. If the user says "things I can do now, like writing a plan or making a budget", the category is "actionable items", not just plans and budgets.
3. Expand at the category level: within each category, find the other members the user didn't mention, especially ones they might not think of on their own (for outreach: interview prep, promoting episodes, following up with guests). Where categories connect, say so (good interview prep means less editing later). Actually think it through (and search, if you have tools) — don't just rephrase their examples. Keep the user's own examples in as named members, but don't let explaining them take over the answer, and don't replace them. Add what is genuinely useful, including whole categories the user didn't think of, but skip filler and stay inside the user's goal.
4. Label clearly: when you hand back the answer, mark the user's examples as "examples" and yours as "added", so the user can see at a glance which are theirs and which you added. Don't mix them together as if all of it came from them.

## When you are not sure

If you can't tell whether it is an example or a requirement, don't guess silently. Pick one of these:

- Ask one question: "Are these examples, or do you want exactly these?" Wait for the answer before acting.
- Or state your assumption and proceed, as in step 1: name the categories you think the examples point to, and invite the user to correct you.

Ask only one question. Don't follow up with more.

## Anti-patterns

Each of these is a way to get this skill wrong. The "tell" is how you can spot it in your own answer.

- **Answering the examples instead of the request.** Tell: most of your answer explains the examples themselves (a full guide to booking guests, a detailed mixing tutorial), and the user's actual request (learning what running a podcast takes) never gets answered at the level they asked.
- **Handing the examples back as the answer.** Tell: your answer contains only the items the user named, nothing added. Doing only those is the same as doing nothing.
- **Turning examples into a task list.** Tell: the user gave 2 examples and you stopped after doing exactly those 2.
- **Treating "the user didn't mention it" as "the user doesn't want it."** Tell: you left something out only because the user didn't say it. They probably just didn't think of it.
- **Over-expanding.** Tell: your additions bury or outrank the user's examples, drift outside the category, or crowd out what the user actually asked for.
- **Replacing the user's examples.** Tell: the user's own examples are missing or demoted in your answer. Expand around them; don't swap them out.

## When NOT to use this skill

- The user gave an explicit closed list ("just these three", "only these", "do exactly this", "nothing else"). Do the list as stated. Do not expand.
- The user gave no examples at all. A bare request with no examples has nothing to expand — do the request as stated.
- The user is illustrating a *format* or *style*, not a category of content (e.g. "write it like this example paragraph"). Do not expand the content; match the format.
- The examples are test cases or exact specs (e.g. "for example, input 3 should return 9"). Treat each one as a hard requirement. You may suggest extra cases, but label them as suggestions.

## Cases (practice on these)

### Case 1: Remind me about one tool — just an example

- User (who has shared several tools before, including "Quick Cut" and "Text Copy"): "When I need to batch-process images, remind me about the 'Image Workshop' tool."
- Wrong: remember only "Image Workshop" and mention only that one when asked.
- Right: recognize the category is "useful tools the user has shared". Besides "Image Workshop", also remember the other tools they shared, like "Quick Cut" and "Text Copy". When they need one, give them the whole set.

### Case 2: Things to learn, like photography, cooking, gardening

- User: "I want to learn many things, like photography, cooking, gardening."
- Wrong: treat these three as the complete list and hand back a three-item plan.
- Right: open with "Got it: photography, cooking and gardening are all hands-on skills you can enjoy and use day to day." The category is "things to learn that might come in handy". These three are just what came to mind. Add what they didn't mention: writing, music, programming, and so on.

### Case 3: Things I can do now, like writing a plan or making a budget

- User: "My action list should have things I can do now, like writing a plan or making a budget."
- Wrong: put only these two items on the list.
- Right: open with "Got it: a plan and a budget are both small things you can start today without waiting on anyone." The category is "actionable items". Besides these two, add others of the same kind, and label them:
  - Your examples: write a plan, make a budget
  - Added: set a deadline, collect one reference example

### Case 4: A French cooking channel

- User: "Make a channel about French cooking for English speakers."
- Wrong: treat "French cooking" as the only topic and plan around it alone.
- Right: recognize the category is "a cross-language content bridge" — explaining one culture to people from another. French cooking is one example; others include French poetry, French history, French film. Pick the bridge first, then choose which topics to build on it.
- Note: there are no marker words here — this is the single-representative case. Still plan the French cooking channel they asked for; the other topics are additions, not a replacement.

### Case 5: A long message with examples buried inside

- User: "I want to learn lots of things that will help me run a podcast, at every level. For example, how to find and invite guests, or how to mix audio so voices sound clear."
- Wrong: write a long guide to finding and inviting guests, then a detailed mixing tutorial. The examples have taken over the answer, and the actual request, learning what running a podcast takes, is never answered.
- Right: open with one plain sentence naming what the examples have in common: "Got it: finding guests and mixing audio, one is about people and one is about sound, both things a podcast needs beyond having something to say." Name the two examples as members of those categories. Then add other skills in the same fields that the user did not mention, such as interview prep and promoting episodes on the people side, and recording setup and editing for pace on the sound side, and point out links between them, such as how good interview prep means less editing later. Label which items came from the user and which you added.

### Case 6: Real plans, not illustrations

- User: "I want to do a few new things, like learning to bake bread or starting to run. How do I start?"
- Wrong: open by sorting them into categories and recommending other things of the same kind (pottery, cycling), with only a few lines on bread and running.
- Right: answer bread concretely (start with one simple loaf, what to buy, what usually goes wrong) and running concretely (run-walk a few times a week, how to avoid early injuries). Then add one separate section at the end, labeled as extra, for anything else worth knowing.
